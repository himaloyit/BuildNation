01 — Recommendation

One new service, not five

Every entity in your write-up could become its own microservice — project, fund, contractor, work order, payment, inspection. That's over-fragmentation for a domain this tightly coupled. The fund→project→work-order→payment chain shares one transactional rhythm and one audience of internal staff, so it should live in one deployable, not five.

A four-way split (fund / project / contractor / work-order) still pays a network hop and an eventual-consistency tax for writes that are really one business transaction — allocating a fund, issuing a work order, releasing a payment all touch the same aggregate. Folding the location hierarchy in too (rather than standing it up as its own reused module) removes another hop, since a project can't be registered without a village. The result is constituency-development-management: one service, one schema, one deployment — plus an extension to the auth module for dynamic roles and audit. Details below.

Two things still stay separate, for reasons that don't apply to the domain services above: security-access-control is a different audience (platform-wide identity, not fund-specific) and already exists as a running service. analytics-reporting is a different lifecycle (read-side dashboards that can lag behind writes and scale independently of the transactional core).

Where this document departs from your list

Your outline separates "inspection" as step 8. I've folded it into the work-order/payment package as a gate on the final milestone, since an inspection with no work order to close doesn't do anything on its own — splitting it out would mean an extra round-trip for every payment release even within one service.

02 — System Architecture

Service map

The new service registers with Eureka and sits behind the existing gateway like member-management does today. 03 — Database ER Diagram

Core entities

Every box below is owned by constituency-development-management and lives in the same schema, so project→sub_category, project→village, work_order→project and work_order→contractor are real foreign keys enforced by Postgres, not resolved over the network. The one exception is submitted_by / inspector_id — those point at users owned by security-access-control, so they stay plain UUID columns resolved by calling that service or reading its Kafka event.

Auth extension

The current UserRole enum (SUPER_ADMIN, ADMIN, MEMBER, VOLUNTEER, VIEWER) can't hold "dynamic roles" — enums are compiled, not admin-configurable. This becomes a real table.

04 — Microservice Design

One deployable, five internal packages

constituency-development-management follows the same layering as member-management (domain/entities, domain/dto, services/iServices + services/impl, controllers/rest) but with the domain split into sibling sub-packages instead of sibling services. The boundary between them is a Java package, not a network call — so it costs nothing to keep them cleanly separated, and nothing stops a later extraction if one genuinely needs to scale independently.

PackageOwnsWhy grouped, not split into its own service
com.himaloyit.buildnation.cdm.regionDistrict → Village hierarchyRead-heavy reference data every other package needs; no reason to pay a network call to resolve a village.
com.himaloyit.buildnation.cdm.fundFund periods, category earmarks, allocations, ledgerAn allocation is meaningless without the period it draws from and the category it's earmarked against — same aggregate, same transaction.
com.himaloyit.buildnation.cdm.projectCategories, projects, priority queue, statusPriority rank is a computed property of the project list itself (re-ranking one project re-ranks the queue) — keeping it out-of-process would mean a distributed transaction for every reorder.
com.himaloyit.buildnation.cdm.contractorContractors, NGOs, committees, work historyOwn onboarding/licensing lifecycle, but still referenced synchronously and cheaply by work orders since it's an in-process call.
com.himaloyit.buildnation.cdm.workorderWork orders, milestone payments, inspectionsAn inspection's only purpose is gating the next payment milestone; a payment's only purpose is fulfilling a work order — approving a milestone and flipping the project's status now happens in one @Transactional method instead of three network calls.

Cross-package calls inside the service are plain Java method calls on the owning package's service interface (e.g. workorder calling IContractorService to validate a contractor before issuing a work order) — no REST, no retries, no timeouts. Kafka is reserved for what actually needs to leave the service: publishing domain events for analytics-reporting and the audit trail in security-access-control.

Cross-service references

Because the whole fund→project→contractor→work-order domain now lives in one schema, those relationships can be real foreign keys with real referential integrity — no more UUID-only links to resolve at read time. The one genuine cross-service reference left is a user id (submitted_by, inspector_id, changed_by) pointing into security-access-control; that one stays a plain UUID, resolved by calling that service or reading its Kafka event, since it's the one boundary that's still a real network hop.

07 — Roles & Permissions

What changes in security-access-control

Seed the existing enum values as rows in the new role table first — that's a zero-downtime migration for member-management — then add the fund-specific roles alongside them. From then on, roles are admin-managed data, not a redeploy.

RoleTypical permissionsOrigin
SUPER_ADMIN, ADMIN, MEMBER, VOLUNTEER, VIEWERUnchangedmigrated from enum
MP_MINISTERApprove projects, approve top-of-queue fundingnew
CONS_PROJECT_OFFICERRegister projects, manage priority inputs, request work ordersnew
ENGINEEREndorse projects, record inspectionsnew
FINANCE_OFFICERAllocate funds, approve payments, issue vouchersnew
  • Table shape: role, permission (resource + action), role_permission, and user_role as a many-to-many — a user can hold Engineer on one constituency and Viewer platform-wide.
  • JWT claim: replace the single role claim with a roles array; authorize with @PreAuthorize against resource/action strings, not role names, so new roles never need a code change downstream.
  • Audit trail: every write service publishes a domain event (project changed, allocation made, payment approved) to a Kafka audit-events topic; security-access-control consumes it and writes audit_log rows — one place to query "who changed what," no service needs direct write access to another's audit table.

10 — MVP Plan

What to build first

The MVP proves the core loop — priority queue in, payment out — without the parts that are safe to bolt on later.

Ship in MVP

  • Project registration + manual status transitions
  • Manual priority ranking (score entered, not computed by formula)
  • Fund period + project-level allocation
  • Single-payment work orders (no milestone split yet)
  • New roles wired into JWT + @PreAuthorize
  • Basic dashboard: totals only, no category breakdown

Defer past MVP

  • Milestone/percentage payment splits
  • Inspection photos and quality scoring
  • Weighted priority-scoring formula
  • Contractor performance ratings
  • Document OCR, category-wise analytics
  • Everything in Section 11
11 — Future AI Features

Backlog, roughly in build order

  1. Priority-scoring model — learn weights for urgency, population coverage and repair cadence from historical funding outcomes, instead of a hand-tuned formula.
  2. Inspection vision — estimate percent-complete from submitted photos and flag duplicate or reused images.
  3. Payment anomaly detection — flag unusual milestone timing or amount patterns per contractor for finance review.
  4. Document OCR — auto-extract voucher and invoice fields on upload instead of manual entry.
  5. Fund demand forecasting — predict next month's category-wise need from the standing priority queue.
  6. Constituent chatbot — Bangla/English project-status lookup by name or location, backed by constituency-development-management's project read API.
